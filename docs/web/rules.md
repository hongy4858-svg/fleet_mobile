# Rules: 개발 규칙, 단위, 데이터 검증 및 보안 원칙 (Supabase Cloud 연동 기준)

본 문서는 "기업 차량 운영 관리 및 친환경차 전환 경제성 분석 시스템"의 코드 일관성, 계산 무결성, Supabase 클라우드 데이터베이스 및 RLS(Row Level Security) 보안을 보장하기 위한 표준 규정입니다.

---

## 1. 표준 단위 및 표기 규격

시스템 내 모든 수치는 데이터 계층(PostgreSQL)에서 **표준 기본 단위의 숫자(Number/Numeric)**로 저장하며, 화면 표시 시 지정된 단위 기호와 천 단위 콤마(`,`)를 함께 렌더링합니다.

| 분류 | 대상 항목 | 내부 저장 단위 | 화면 표기 형식 | 비고 |
| :--- | :--- | :--- | :--- | :--- |
| **금액** | 구매가, 매각가, 정비비, 에너지비, PV 등 | 원 (`KRW`) | `#,###원` (정수) | 소수점 발생 시 반올림 처리 |
| **거리** | 운행 주행거리, 연간 예상 주행거리 | 킬로미터 (`km`) | `#,### km` | 0 이상 실수/정수 |
| **기간** | 분석 기간 | 년 (`years`) | `#년` | 1 ~ 30 양의 정수 |
| **할인율** | 경제성 분석 할인율 | 백분율 (`%`) | `#.##%` | 0% 이상 실수 (예: 4.5, 0% 허용) |
| **연료 주입량** | 가솔린, 디젤, 하이브리드 | 리터 (`L`) | `#,###.# L` | 소수점 1~2자리 허용 |
| | 전기 (EV) | 킬로와트시 (`kWh`) | `#,###.# kWh` | 소수점 1~2자리 허용 |
| | 수소 (FCEV) | 킬로그램 (`kg`) | `#,###.## kg` | 소수점 1~2자리 허용 |
| **연비** | 가솔린, 디젤, 하이브리드 | `km/L` | `##.# km/L` | 0 초과 필수 |
| | 전기 (EV) | `km/kWh` | `##.# km/kWh` | 0 초과 필수 |
| | 수소 (FCEV) | `km/kg` | `##.# km/kg` | 0 초과 필수 |
| **에너지 단가** | 가솔린, 디젤, 하이브리드 | 원/L | `#,###원/L` | 0 초과 필수 |
| | 전기 (EV) | 원/kWh | `#,###원/kWh` | 0 초과 필수 |
| | 수소 (FCEV) | 원/kg | `#,###원/kg` | 0 초과 필수 |

## 2. 데이터 무결성 및 관계형 제약조건 규칙

### 2.1 사용자별 차량번호 중복 방지
- 동일 사용자(`owner_id`) 내에서 동일한 차량번호(`plate_number`)의 중복 등록을 원천 방지합니다.
- DB 제약: `CONSTRAINT uq_vehicles_owner_plate UNIQUE (owner_id, plate_number)`

### 2.2 타 사용자 차량 연결 방지 (복합 외래키 제약)
- 악의적이거나 비정상적인 요청으로 다른 사용자의 `vehicle_id`를 자신의 운행, 주유, 정비 기록에 연결하는 것을 원천 차단합니다.
- `vehicles` 테이블에 `UNIQUE (id, owner_id)`를 지정하고, 하위 기록 테이블들(`trip_logs`, `energy_logs`, `maintenance_logs`)이 `FOREIGN KEY (vehicle_id, owner_id) REFERENCES vehicles(id, owner_id) ON DELETE CASCADE` 복합 외래키를 참조하도록 강제합니다.

### 2.3 분석 이력의 불변 스냅샷(Immutable Snapshot) 보장
- 경제성 분석을 저장할 때에는 차량 정보가 향후 수정되거나 삭제되더라도 영향을 받지 않도록, 분석 당시의 모든 입력 파라미터(`input_snapshot`)와 산출 결과(`result_snapshot`)를 PostgreSQL의 **`JSONB` 컬럼에 완전한 Deep Copy 형태로 영구 보존**합니다.

## 3. 보안 및 Supabase 인증 규칙

### 3.1 RLS (Row Level Security) 전면 활성화
- Supabase의 6대 테이블(`vehicles`, `trip_logs`, `energy_logs`, `maintenance_logs`, `replacement_candidates`, `analyses`) 모두에 RLS를 활성화합니다.
- 인증된 사용자(`authenticated`)에게만 접근 권한을 부여하며, 모든 DML은 `auth.uid() = owner_id` 조건을 만족해야만 수행됩니다.

### 3.2 환경변수 및 API 키 보안
- 클라이언트 브라우저에는 오직 `VITE_SUPABASE_URL`과 `VITE_SUPABASE_ANON_KEY`(또는 publishable key)만 주입합니다.
- **`service_role` 키나 데이터베이스 비밀번호는 클라이언트에 절대 포함하지 않습니다.**
- `.env.local` 파일은 `.gitignore`에 등록되어 GitHub 등 형상관리에 커밋되지 않도록 차단합니다.

### 3.3 클라우드 연결 오류 처리 원칙
- Supabase 연결 실패, 네트워크 오류, RLS 권한 오류 발생 시 **오류를 은폐하거나 브라우저 로컬 저장소(localStorage)로 자동 전환(Fallback)하지 않습니다.**
- 명확한 에러 원인 배너를 화면에 표시하여 사용자가 올바른 환경변수 설정과 SQL 마이그레이션을 진행할 수 있도록 안내합니다.
- 기존 로컬 저장소에 남아있는 데이터는 임의 삭제하거나 클라우드로 무단 자동 업로드하지 않습니다.

### 3.4 시연 데이터 계정별 격리 생성 및 초기화
- 시연 데이터(가상 차량 5대, 운행 19건, 주유 17건, 정비 7건, 후보 3종)는 로그인 후 사용자가 상단 **[시연 데이터 생성]** 버튼을 클릭했을 때 **현재 로그인한 사용자 계정(`auth.uid()`)에만 중복 없이 주입**됩니다.
- 클라우드 데이터 초기화도 현재 로그인한 사용자의 데이터에만 국한하여 실행됩니다.

## 4. PWA 작업 규칙
- 기존 기능, 경제성 계산 공식, 인증 및 DB 관련 코드는 수정하지 않는다.
- 오프라인 캐시를 추가하지 않는다. 서비스 워커에서 Cache API, 사전 캐싱, 요청 가로채기를 사용하지 않는다.
- PWA 변경은 manifest, 아이콘, 최소 서비스 워커 및 연결·등록 코드로 한정한다.
- 설치 확인 전까지 P3는 완료로 표시하지 않는다.
